Branch Visualizer · Redesign

Three directions for the same app.

Each window below is the real layout — repo header, branch pane, commit graph with rails, an expanded commit, the uncommitted-changes strip — rendered from one identical dataset. Nothing about the structure changes between them. What changes is the entire visual language: palette, density, type, chrome, and how the graph rails read.

That's the whole thesis of the rebuild: once the look lives in a token layer, swapping between these is a values change, not a rewrite.

Pick one — or mix (e.g. Graphite's density with Paper's light ground). Scroll each window horizontally if it's wider than your screen. The toggle top-right only restyles this page's chrome; each window keeps its own committed look.

However we go — build it token-first

All three windows above share the exact same markup and data; only a set of variables differs. That's not a mockup trick — it's the delivery plan. The current code hardcodes every color and size inline across six files, twice (light + dark). We fix that once, then the chosen look is a small diff.

00

Lock the direction

You pick A / B / C (or a blend). I turn it into concrete tokens: palette, radius, base size, row height, rail style.

01

Token layer

Define the palette as CSS variables mapped through Tailwind v4 @theme inline, with a .dark override. One place owns the whole look — and every inline dark: variant disappears.

02

Mechanical sweep

Swap raw neutral-* / blue-* utilities for the semantic tokens, file by file. No visual change yet — pure re-plumbing (good to hand off to a bulk model).

03

Apply + polish

Set the token values to the chosen direction, tune the graph rails (ROW_H / LANE_W are already constants), then per-component spacing where the look needs it.

Approve a direction — A, B, or C, or a blend (e.g. Graphite density + Paper's light ground) — and say the word to build it token-first. Nothing in the repo changes until then; this file is a throwaway you can delete.
